## RR1 · P1（原 R2）：准备阶段取消可永久占用任务锁

位置：`HomeViewModel.kt:342–364` 与 `529–542`。
https://github.com/heDuke/DSU-Sideloader-RE/blob/0ef87b30a9e98b44b8f1b891d78a8908c20c3712/app/src/main/java/vegabobo/dsusideloader/ui/screen/home/HomeViewModel.kt#L342-L364

beginTask 先占锁，然后 `launch(Dispatchers.IO + job)`。协程内两次 `readBoolPref` 在 try 外面。用户在偏好读取挂起期间取消，CancellationException 不进入现有 catch，PREPARING 分支又假设准备协程会报告取消，因此没有 finish。

更早取消、导致协程尚未开始执行时，也不会进入函数体的 try/finally。仅把偏好读取移进 try 还不足以覆盖这个入口。

复现模型采用生产 gate 和相同的协程边界：在初始偏好读取处挂起，requestCancel + job.cancel，等待协程结束，输出：

```text
terminal=false busy=true
```

结果是界面一直 CANCELLING，新安装始终被拒绝。偏好读取异常也位于保护范围之外。

要求：

- 将整个准备入口纳入异常与取消处理。
- 对“协程未开始就取消”注册幂等完成兜底，确保有且只有一次终态处理。
- 不能在后端仍在执行时提前 finish；按实际任务阶段处理交接。
- 增加真实 ViewModel/协调层测试：派发前取消、偏好读取中取消、偏好读取抛错，均释放 gate 并显示准确终态。

证据边界：生产 gate + 等价协程模型、源码定位；不是 Android ViewModel 集成复现。

## RR2 · P1（原 R2）：取消完成后仍会提交旧系统安装请求

位置：`DsuInstallationHandler.kt:27–37`、`HomeViewModel.kt:529–580`；关联原有 `PrivilegedProvider.kt:16–39`。
https://github.com/heDuke/DSU-Sideloader-RE/blob/0ef87b30a9e98b44b8f1b891d78a8908c20c3712/app/src/main/java/vegabobo/dsusideloader/installer/privileged/DsuInstallationHandler.kt#L27-L37

handler 使用 PrivilegedProvider 的独立 IO 协程，既没有 task ID/cancellation token，也不返回可等待的执行句柄。ViewModel 的 installationJob.cancel 不能停止它。取消路径独立 forceStop 然后 finish，不能保证旧提交已经停止。

执行实际 handler/provider，用存储读取暂停旧请求；模拟 ViewModel 的 shell 取消顺序，待取消已结束后释放读取，实际调用顺序：

```text
forceStop
cancel-finished
unmount
forceStop
startActivity-after-cancel=true
```

旧请求在取消结束后才卸载卡、打开安装确认页面。UI 回调按 ID 丢弃只保护显示，不能阻止这些副作用；此时 gate 还可能允许下一任务开始。

要求：

- 让系统安装提交成为当前任务可取消、可等待的步骤。
- 在服务等待、持久化及卸载之后，提交 intent 之前核对取消状态。
- 取消终态前等待旧提交真正停止，并把提交/取消的副作用串行化。
- 捕获该任务的不可变安装参数，避免旧请求读取后来改变的共享 session。
- 添加“提交前阻塞 → 取消完成 → 释放阻塞”测试，确认不会再 unmount/startActivity；覆盖慢卸载与服务等待。

证据边界：真实 handler/provider/gate，受控服务和存储；取消协调步骤按 ViewModel 顺序重现，未实例化 Android ViewModel。

## RR3 · P1（原 R3）：启动计数变化覆盖了明确的“正在安装”状态

位置：`SdCardRemounter.kt:138–146`，即 RemountPolicy.onAppStart。
https://github.com/heDuke/DSU-Sideloader-RE/blob/0ef87b30a9e98b44b8f1b891d78a8908c20c3712/app/src/main/java/vegabobo/dsusideloader/installer/privileged/SdCardRemounter.kt#L138-L146

当前先判断 bootId 不同，并直接返回 Remount，完全忽略传入的 `state == INSTALLING`。

真实策略类复现：

```text
record.phase = SYSTEM_UNKNOWN
record.bootId = "7"
currentBootId = "8"
state = INSTALLING
实际：Remount(reason=device rebooted since unmount)
应为：Prompt / 阻止自动挂载
```

即使旧安装会话不会跨重启保留，也不能推出当前没有新安装。系统或其他客户端可以在重启后重新发起安装；应用启动检查也是异步执行的。

要求：已知正在安装必须优先阻止自动恢复。bootId 变化仅能说明跨过重启，不能覆盖当前活动状态。state=UNKNOWN 时，首个稳定版建议保留提示，待设备证据充分后再开放自动策略。新增各状态与 bootId 组合测试。

证据边界：直接执行生产 RemountPolicy，不依赖真机假设。

## RR4 · P2（原 R4）：无法确认挂载状态时仍删除恢复记录

位置：`SdCardRemounter.kt:260–267`。
https://github.com/heDuke/DSU-Sideloader-RE/blob/0ef87b30a9e98b44b8f1b891d78a8908c20c3712/app/src/main/java/vegabobo/dsusideloader/installer/privileged/SdCardRemounter.kt#L260-L267

isMounted 返回 null 或查询异常时，getOrNull 得到 null，当前逻辑“相信 mount() 的结果”并返回成功。之后恢复记录被清空。但 mount 是 void 请求，调用返回不代表挂载已完成；状态未知也不等于成功。

实际 remounter 注入：当前列表仍有该卷，mount 正常返回，isMounted 抛暂时查询错误。输出：

```text
remaining=[] record=null
```

这仍然会丢失恢复责任，只是从 mount 调用失败转移到了状态查询失败。

要求：null/查询异常保留 pending 和“无法确认挂载状态”的原因，后续查询确认挂载或确认卷不存在后再清除。三秒超时同样应保留记录。更新目前依靠默认 isMounted=null 就断言挂载成功的测试替身，不能让测试把未知当成功。

证据边界：直接执行生产 SdCardRemounter，使用受控 VolumeOps/存储，不是设备测试。

## 对本轮待定事项的建议

1. **提交顺序**：不用为了排序 rebase 已推送历史，不构成阻塞。按修复内容和最终测试审查即可。
2. **无 root 取消**：可以显示“已请求取消，清理结果无法确认”，这是可接受的保守结果。但必须先解决 RR2，保证不会再提交旧请求；文案不能掩盖仍在运行的提交协程。
3. **重启后恢复挂载**：已知 INSTALLING 必须阻止。BOOT_COUNT 变化加 UNKNOWN 暂时仍提示用户。可确认已挂载的卷只需清除旧记录，不需要再发 mount。
4. **安装中判断**：getInstallationProgress().status 的查询失败属于 UNKNOWN；SYSTEM_UNKNOWN 的确认弹窗阶段不自动挂载，这一方向正确。状态常量和各版本语义需对照平台并做设备验证。
5. **VolumeInfo / 轮询三秒**：三秒可以作为一次验证窗口，超时表示未确认而不是永久失败；保留记录以便稍后验证。查询失败不得当成功。
6. **URL ZIP 预检**：P0 可接受流式来源无法提前完整列举的限制，前提是同样的规则在 finish 前执行、失败准确清理。默认先下载并校验的完整流程仍留待后续阶段。
7. **翻译处理**：本轮逐字符串、有说明的局部 MissingTranslation 抑制方向可接受；补齐其他语言继续作为维护项。未独立运行 lintDebug，不能替作者的结果背书。
