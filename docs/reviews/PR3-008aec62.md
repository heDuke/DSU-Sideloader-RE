### 取消复现

1. 非 root、具备 READ_LOGS 的任务 A 第一次卸载卡并 startActivity；请求步骤完成，界面仍为 WAITING_USER_CONFIRMATION，存在真实的重试按钮。持久化记录为 SYSTEM_UNKNOWN，系统 DSU 应用的结果未确认。
2. 用户重试。新请求已经完成登记、覆盖 dsuSubmission，但在第二次 unmount 的 IPC 中暂停；尚未执行新请求的 forceStop/startActivity，所以它自己的 reachedSystem=false。
3. 用户取消。代码正确等待重试步骤和阻塞请求停止。
4. 因为只看最新 step 的 false，直接显示“已取消”；**没有停止第一次打开的系统 DSU 应用，没有验证其安装残留，就自动 mount 并清空先前 SYSTEM_UNKNOWN 记录。**

输出：

```text
REVIEW history before retry:
phase=SYSTEM_UNKNOWN calls=[unmount-1, forceStop, startActivity]

REVIEW cancelled retry:
card=ERROR_CANCELED
calls=[unmount-1, forceStop, startActivity, unmount-2, mount]
pending=null uncaught=[]
```

forceStop 只有第一次请求准备时的那次；取消之后没有新增 forceStop。最新请求虽然未到达系统，之前的系统提示或安装仍可能存在。此处不声称真机上必然已开始写分区，但“已取消且可以安全恢复卡”没有证据。

### 失败复现

同样先完成第一次交接，然后让第二次重试在写入待恢复记录时发生一次 IOException（模拟 DataStore 的持久化故障）。该错误在新的 unmount / forceStop / startActivity 之前出现；DsuSubmission 将其返回 Failed，onTaskFailed 直接结束任务并恢复旧卡。

```text
REVIEW failed retry:
card=ERROR
calls=[unmount, forceStop, startActivity, mount]
pending=null uncaught=[]
```

两个 probe 均要求“不能自动 mount”，实际 mount=1，断言失败。没有靠协程异常泄漏造成失败。失败 probe 还要求保留之前未确认的记录。

### 为什么现有测试没有发现

仓库的 DSU 重试取消 probe 在 currentBootId 参数捕获阶段暂停，**尚未登记第二个提交 step**。取消时仍能读到第一个 reachedSystem=true 的 step，故会 forceStop 并给出“清理无法确认”，该测试确实通过。

新增场景在第二个 step 已登记之后暂停，旧的 reachedSystem=true 已从共享字段中丢失。单个请求的发送互斥和按顺序 join 都成立，也不能证明该任务之前交给系统的动作已结束。

### 最小修复要求

- 系统交接的不确定性应按 task 保留，不能被后续尚未交接的重试降级成“从未到过系统”。可以保留任务级交接历史，或采用等效协议；不要求重写引擎。
- 取消最新请求之后，如果任务任意较早请求仍有未确认系统交接，继续执行原有系统取消/清理策略。root 下只有验证清理完成才能报告干净取消；无 root 保持“已请求取消，清理结果无法确认”，保留待恢复记录，不自动挂载。
- 重试失败也不能仅凭“本次失败”就认定之前的系统动作已经结束。失败应保留原交接的不确定性，安全结束/提示的策略与取消保持一致。
- 只有确认整项系统安装终止、或显式允许的恢复操作，才能消除这份不确定性及恢复卡。不能通过清空 pending 或把 SYSTEM_UNKNOWN 改为 LOCAL_TASK 绕过。
- 补充两个真实接线回归：已交接 A → 登记 B → B 交接前取消；已交接 A → B 的持久化 I/O 失败。保留“从未交接的首次任务”可正常取消清理的正向场景，以及现有单请求不并行/先等待再收尾断言。

这是本 PR 要覆盖的“重试后取消/失败”的任务归属边界，不把祖先代码中可能已有的同类风险一概声称为本提交新引入。此前 FR1 关闭结论不变。
